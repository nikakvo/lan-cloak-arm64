1 · what this module does

A VPN hides what the phone does on the internet. It cannot hide what the phone tells the local network it is connected to: the router of a hotel, a café, an office or your own home. Every phone on Wi-Fi does that all the time:

  • When it connects, it asks the router for an address (DHCP) and sends its device name (for example POCO-F6-Pro), the text android-dhcp-16 (Android and its version) and a list of settings that is typical for Android.
  • While connected, it announces itself and its apps to every device on the network (mDNS, SSDP) and sends name lookups to all of them (LLMNR): which cast and media apps are installed, Xiaomi's HyperConnect, and the like.

LAN Cloak removes that: the DHCP request is cleaned in the kernel on its way out, and the announcements are dropped by the firewall before they leave the phone. Every part is a switch of its own.

It works on Android's Wi-Fi client interface only (normally wlan0). Hotspot interfaces, mobile data and VPN tunnels are never touched.

needs
KerneleBPF and tc classifiers: CONFIG_BPF_SYSCALL, CONFIG_NET_CLS_BPF, CONFIG_NET_SCH_INGRESS - in every Android GKI kernel. The installer loads the DHCP cleaner once to check; without these, only the announcement blocking works.
Devicearm64.
RootSukiSU Ultra, KernelSU, APatch or Magisk (WebUI through MMRL / KSU WebUI Standalone).
Tested on a Poco F6 Pro with Xiaomi.eu HyperOS 3 (Android 16) and an android13-5.15 GKI kernel. The DHCP client is Android's own (NetworkStack), the same on every ROM, but other phones are not tested.
2 · quick start
  1. Flash the zip, reboot. Everything is on by default.
  2. Open the WebUI. The top shows Seen by the router: four magenta tiles = nothing to see.
  3. Tap Restart Wi-Fi (twice, to confirm) so a clean DHCP request goes out now. Dashboard → DHCP guard → Last request says cleaned.
  4. Do you cast to a TV or a Chromecast, or print over Wi-Fi? Settings → turn Block mDNS (and for DLNA TVs Block SSDP) off. See 5.

Your router may still list the old device name: it keeps it with the address lease until the lease ends (often 12 or 24 hours), or until you remove the device in the router's page.

The three switches

switchDHCP optionwhat it does
Hide the device name12, 81Removes the host name (the device name from Settings → About phone, made DNS-safe) and the FQDN option. The router lists the phone without a name.
Hide the vendor class60Removes android-dhcp-<version>. The router does not learn the operating system or its version from it.
Generic request list55Keeps the 9 settings every client asks for and drops Android's typical extra ones (see below). Systems that identify devices on a network (the "fingerprint" databases routers and firewalls use) recognise Android by this list alone.

The generic list

Kept: 1 subnet mask, 3 router, 6 DNS servers, 15 domain name, 26 MTU, 28 broadcast address, 51 lease time, 58 / 59 renewal times. Dropped: 43 vendor-specific information, 114 captive portal address, 108 "IPv6-only preferred". Nothing the phone needs is lost: Android finds a hotel login page by its own network check anyway, and without 108 the phone simply keeps IPv4 on networks that offer an IPv6-only mode.

How it works

A small eBPF program sits on the Wi-Fi interface (tc egress filter, priority 10, named lan_cloak_dhcp). It looks only at DHCP requests from the phone (UDP 68 → 67) and overwrites the chosen options with padding in place: the packet keeps its length, the checksum is corrected, nothing is ever dropped. Everything else passes untouched. Options that stay: the client ID (the MAC address, as always), the requested address, the maximum message size.

Android deletes the interface's traffic-control setup every time Wi-Fi goes off, and with it every filter. The DHCP guard (a small daemon, lanc-bpf watch) follows the interface and puts the cleaner back within about half a second - seconds before Android sends its first request when Wi-Fi connects again. It starts at early boot, so the first request after a reboot is clean too.

When a change applies

With the next DHCP request: when Wi-Fi connects, or when the lease is renewed (halfway through the lease). Restart Wi-Fi in the WebUI sends one now.

In logcat you will see E/netd: tcQdiscAddDevClsact(...[wlan0]) failure: File exists each time Wi-Fi comes on. That is the guard having set things up before netd: harmless, netd's own filters work the same.
5 · announcements: mdns, ssdp, llmnr
switchblocksstops working while on
Block mDNSUDP 5353 to 224.0.0.251 / ff02::fb, and answers from port 5353Casting to a TV / Chromecast (Google Cast), Spotify Connect and similar "play on" lists, finding printers over Wi-Fi, Xiaomi HyperConnect / Mi Share discovery, other apps that look for devices nearby.
Block SSDPUDP 1900 to 239.255.255.250 / ff02::c / ff05::c, and answers from port 1900UPnP / DLNA: casting to DLNA TVs, media servers, some smart-home apps.
Block LLMNRUDP 5355 to any multicast address, answers from port 5355 (UDP and TCP)Nothing common on Android.

The phone still receives other devices' announcements; it just never answers or announces itself. If you cast at home only, switch mDNS (and SSDP) off for a moment while casting, then on again - the switch acts at once, no reboot.

How it works

Two firewall chains, LANC_OUT (IPv4) and LANC_OUT6 (IPv6), each with one jump at the end of OUTPUT and only for the Wi-Fi interface: -A OUTPUT -o wlan0 -j LANC_OUT. They only drop, never accept, so nothing of Android's or another module's rules is skipped. The watchdog puts them back if anything removes them.

Dashboard → Announcements blocked counts the dropped packets. The counters start at 0 whenever the rules are set again (boot, a change of settings).

6 · states and the dashboard
statemeaning
cloakedEverything selected is in place. With Wi-Fi off the banner says Cloak ready: the guard waits and acts the moment Wi-Fi connects.
errorA part could not be set: the DHCP guard did not start (the kernel refused the program - the Log has the kernel's report), or the firewall rules failed. The other part keeps working. A failed guard is retried every 5 minutes, or at once with Check now.
offSwitched off in Settings, every option off, or the module disabled in the root manager. Wi-Fi works exactly as Android does it; nothing of the module is active.

DHCP guard

Guard: the daemon runs. Cleaner on the interface: the eBPF filter is in place right now (with Wi-Fi off it waits for Wi-Fi). Last request: when the phone last sent a DHCP request and whether anything was removed. Requests seen / cleaned and Removed: counted since the guard started. skipped (orange) counts requests with an option too long to rewrite safely; they were sent unchanged - send the Report if it ever appears.

Watchdog

Every 10 seconds (every 2 seconds in the first 2 minutes after boot) it checks that the guard runs with the right settings on the right interface and that the firewall rules are complete, and repairs what is not. Repairs are written to the Log.

Log

Module: what the module did (starts, changes, repairs). DHCP guard: the guard's own log - every time Wi-Fi goes off and on, who removed the filter, how fast it was back.

7 · with wg shield, dnscrypt proxy, vpn hotspot and ipset
what the local network sees of the phone → LAN Cloak
where internet traffic goes → WG Shield
name lookups → DNSCrypt Proxy

Each module has one job and works alone; together they cover the phone on a foreign Wi-Fi. LAN Cloak's Dashboard shows whether the others are installed and what they are doing.

  • WG Shield: unrelated rules (routing there, an eBPF filter and firewall chains here). The tunnel, Android's network check and the hotel login page work the same with LAN Cloak.
  • DNSCrypt Proxy: without it, the router sees every name the phone looks up. LAN Cloak does not change DNS.
  • VPN Hotspot: the hotspot interfaces are not touched; hotspot devices announce themselves as they always would. A hotspot while connected to Wi-Fi works as before.
  • ipset: independent.
8 · what it does not hide
  • The MAC address. The router always sees one. Android uses a random address per network by default (the WebUI says randomized by Android); the same network sees the same random address each time, so it still recognises the phone when it comes back.
  • That a device is there: its address, how much it sends and when. That is what a router is for.
  • Android's network check (a request to Google's generate_204 on every new network) and the traffic around connecting: that is the VPN's part (WG Shield sends everything else through the tunnel).
  • The device name elsewhere. Android may also show it as the Bluetooth, hotspot and Wi-Fi Direct name; LAN Cloak only keeps it out of DHCP.
  • Other networks. Hotspot devices, mobile data (the carrier sees the SIM and the phone anyway), USB and Ethernet adapters.
9 · command line

Every WebUI action is a ctl.sh command. From Termux:

su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh status'   # fresh check, everything
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh set BLOCK_MDNS 0'   # mDNS allowed
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh set BLOCK_MDNS 1'
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh set ENABLED 0'   # everything off
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh dhcp'   # the cleaner's counters
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh wifi-restart'   # new DHCP request now
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh sync force'   # check, repair, retry the guard
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh log 100'
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh guardlog 100'
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh diag'   # report
su -c '/system/bin/sh /data/adb/modules/lan-cloak/ctl.sh help'   # every command and setting

Settings: ENABLED, DHCP_HOSTNAME, DHCP_VENDOR, DHCP_PRL, BLOCK_MDNS, BLOCK_SSDP, BLOCK_LLMNR (each 0 or 1), WIFI_IFACE (auto or an interface name).

To see a request yourself, capture on the phone (for example from a Linux chroot): tcpdump -i wlan0 -n -vvv 'udp port 67 or udp port 68', then Restart Wi-Fi. No Hostname, no Vendor-Class, and Parameter-Request with 9 entries.

10 · troubleshooting

The router still shows the phone's name

It remembers it from an earlier lease. Remove the phone in the router's device list, or wait until the lease ends. New requests carry no name (check Dashboard → Last request: cleaned).

Casting, printing or "devices nearby" stopped

That is mDNS (and SSDP for DLNA) being blocked - switch them off in Settings. See 5.

"DHCP guard failed"

The kernel refused the cleaner. The Log has the kernel's own report; send the Report. Announcements stay blocked meanwhile, and Wi-Fi works normally (only uncleaned).

"Firewall rules repaired"

Something removed or changed the module's rules; the watchdog put them back. Once now and then is harmless. If it repeats every few seconds, another module fights over the same rules - send the Report.

Wi-Fi does not connect

The cleaner never drops packets, so this is not expected. To rule the module out: Settings → LAN Cloak off (everything is removed at once), or disable it in the root manager - also at once, no reboot needed.

Watchdog not running

Reboot. If it stays stopped, the Log says why.

11 · files, update, uninstall

Update: flash the new zip, reboot. Settings stay. The running version keeps working until the reboot.

Disable in the root manager: the guard stops, the filter and the rules are removed at once. Enable again: back within 10 seconds.

Uninstall: everything is removed, then the data folder is deleted.
